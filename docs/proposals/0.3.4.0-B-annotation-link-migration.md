# 0.3.4.0-B｜Annotation 规则链接与取证版本分离候选

关联 Issue `#73`。本文件是**有界迁移候选与判据**，不是迁移执行记录、不是 DESIGN APPROVE，也不是第二份维护规范。本文不写 Figma，不改变产品规则或图形控件。

## 1. 目的与硬边界

Issue #73 的候选目标是把两类信息分开：

- 现行规则入口：默认分支 `main` 上的稳定 Markdown 锚点（`blob/main/路径#anchor`）；
- 图面／注释当时依据的版本：独立短 SHA；
- 旧图取证版本：继续单列，不追溯改写。

本候选遵守 Issue 正文的边界：

- **不得重新复制规则全文**；
- **不得把版本标记变成第二真源**；
- **不改产品规则或图形控件**；
- 公开面**不泄露内部节点定位**。

PNG、annotation 或固定 SHA 只能说明各自的取证范围，不能证明运行时行为或持久化行为。真实 Figma 写入若另行授权，必须另做 fresh before、单 writer、整组回读和独立 live review；本候选不构成该授权。

## 2. 审计输入与时点边界

Issue #73 唯一来源审计评论（2026-09-22T02:52:36Z）报告的是一个离线组合样本：97 个宿主、117 条 annotations；108 条有链接，共 125 次固定 SHA URL 引用、28 个不同目标，全部固定在同一 commit；另有 9 条没有完整仓内 Owner 的局部说明。

该评论同时给出三组候选计数：

| 组别 | 审计计数 | 审计建议 | 本候选状态 |
|---|---:|---|---|
| 已有显式稳定 Owner 锚 | 110 次 URL 引用／22 个目标 | 可形成 `blob/main/路径#anchor` 候选 | 仅形成候选，不执行 |
| 当前导航仍依赖标题自动锚 | 10 次／3 个目标 | 先补稳定定位或选等价 Owner 入口 | 阻断迁移 |

| 无完整仓内 Owner | 9 条、无 URL | 保留局部说明和未核边界 | 不补链、不删 |

**时点性限制：**上述数字来自该审计时点，不是当前实时 Figma 盘点。后续已有画布写入或 annotation 承接会使宿主、条数、目标和引用次数发生变化；不得把 97／117 或 110／10／5／9 读成当前存量。执行前必须重新取得与目标范围一致的 fresh 快照，并把快照时点和通路落在私有证据中。

## 4. 三类候选判据

### 4.1 可机械迁移候选

只有同时满足以下条件，目标才可进入后续明确迁移数组：

1. fresh 快照确认该目标仍属于“已有显式稳定 Owner 锚”组；
2. 每个引用的规则入口都能解析为同一 Owner 文件中的稳定 Markdown 锚点；
3. 替换只改变规则入口的 ref，从固定 commit 改为 `blob/main/路径#anchor`，不改摘要、状态、局部视觉说明或取证字段；
4. 目标的独立短 SHA 与旧图取证版本字段已分别存在且可回读；若字段不存在，这不是“只改链接”，应移到结构变更审查；
5. 写前、写后能够对拍目标条数、链数、摘要文本、版本字段、未承接局部说明及排除集。

任一条件不满足，就不能标为可机械迁移。

### 4.2 先补锚／选等价入口

“产品拓扑与三栏”“组件卡＋焦点编辑栏”“读图记号与纪律”这 3 个导航目标仍依赖标题自动锚。它们当前链接可能可解析，但不能因此直接归入稳定锚机械迁移。必须先在 Owner 文档建立稳定定位，或由 Owner 明确等价稳定入口；补锚本身是独立文档变更，不在本候选中执行。

### 4.3 保持不动

图面／历史证据组的 5 次引用继续固定在原 commit。旧帧几何登记、节点回读、来源漂移历史证据不能因为标题含有“Current”就改成活动规则入口。若旧条目没有可证明的设计或验收依据，不得把旧规则链接版本改称图面依据版本；未知仍写未知。

9 条没有完整仓内 Owner 的局部说明保留原文和未核边界；不得补造链接，也不得因没有 URL 删除。

## 5. SHA 与登记结构的独立审查边界

本候选**不声称当前 annotation 已经存在**“独立短 SHA 版本列”或“旧图取证列”。这两列在本候选中只是应分别核验的目标字段和审查要求，不是本候选新增的结构。

如果 fresh 盘点发现任一字段不存在，新增字段或登记载体属于结构变更，必须单列 proposal、单独审查、单独取得授权；不能夹在“规则链接迁移”里，也不能用链接替代字段。版本标记只作取证索引，不得升级为产品规则真源。

## 6. 后续执行的最小判据

后续另立执行单时，审阅者至少应能机械判定：

1. 目标集合来自同一 fresh 快照，且作用域明确；
2. 22 个目标的聚合计数与逐目标引用次数相加关系可核；
3. 只有显式稳定 Owner 锚目标进入迁移数组；标题自动锚、图面／历史证据和无 Owner 目标不被顺带改写；
4. 每条迁移只替换规则入口，不复制规则全文，不改产品规则、图形控件、状态或局部视觉说明；
5. 独立短 SHA 与旧图取证字段各自有值、各自有来源；未知不得补造；
6. 写前／写后对拍证明排除集未被静默删除；
7. 公开材料不含内部文件标识、内部对象编号、内网 URL 或凭据；
8. 通过 exact-head DESIGN／REVIEW 后，任何新提交都使旧判词失效并需按新 head 重审。

**判据逐字：**

> 目标只能在 fresh 快照确认其属于“已有显式稳定 Owner 锚”组、其规则入口解析到同一 Owner 文件的稳定 Markdown 锚点、且替换仅改变规则入口 ref 而不改变摘要、状态、局部视觉说明、独立短 SHA 或旧图取证字段时，才可进入后续迁移数组；标题自动锚、图面／历史证据和无完整 Owner 的目标不得进入该数组。若独立短 SHA 或旧图取证字段不存在，必须另立结构变更审查，不得把新增字段夹在链接迁移中。

## 7. 明确不做

- 本候选不执行 annotation 迁移；
- 不写 Figma，不读或改产品规则；
- 不复制规则全文；
- 不把固定 SHA、短 SHA 或图像登记当成第二真源；
- 不改产品规则、图形控件、布局或运行实现；
- 不公开内部节点定位、文件标识、凭据或内部 URL；
- 不产 DESIGN APPROVE，也不替代后续独立 live review。
