# Proposal C｜开放决策

状态：Working Design / Candidate。这里只列尚未收口的问题，不把它们写成现行规则。

## 1. Owner 缺口

- Temporal Opportunity / exposure 到 Candidate reducer 的正式 Current Owner；
- Feeding、Defense、Investigation 的 Interaction composition；
- `SuspicionLoad` 的生产 cue owner；
- 若未来启用 `ExplicitDirectional` bearing prior，production directional support 的 owner。

## 2. 语义缺口

- sibling prey response 的 partial-resolution bounds 是否取得正式 owner；
- Horizontal2D 对 vertical-dominant presentation 的适用状态，是 `NotApplicable`、`Incomplete` 还是另一种结果；
- Opportunity geometry 与 Closing 的联合职责；
- `max_recent` 是否足以表达持续的 erratic movement；
- 装配版本变化时，共用轨迹记忆可以保留到什么边界。

## 3. 标定缺口

- FoodValue relation anchors 的生产来源；
- `K_mot` 的 production value；
- `StateTrigger` 的最终预算；
- `K_close`、`K_pred`、`tau_recover`、`K_wary`；
- `M0 / M1` 的 reference calibration；
- prey support、response、opportunity 和 Candidate 的整链分布；
- saturation 和 zero-response guardrails。

## 4. 数据缺口

- 实际水流与相对水体速度的稳定来源；
- vertical-dominant presentation 的完整轨迹和参考系；
- 鱼与饵的 encounter geometry、reaction window 和 strike reach；
- exposure 的时间窗口、局部范围和单位；
- 各鱼种 `InterceptSpeedLimit` 与体型缩放来源；
- 猎物解释所需的可见性、遮挡和装配局部数据。

## 5. 本轮不做的事

- 不把 Working seed 升格为 production parameter；
- 不把 Proposal C 研究分支的文件当作当前 Contract；
- 不为缺少 owner 的内容补造公式；
- 不通过新增 runtime cap 掩盖重复计权或标定失败；
- 不在完成语义契约前继续扩展商品类型或实现字段。

## 6. 下一轮收口顺序

1. 为 `ActualPresentation`、`PreyInterpretation` 和 `PreyConditionedState` 各选一组完整案例；
2. 明确状态传播和持续记忆的最小规则；
3. 检查第 5 步 FishCondition 是否只消费已解析的上游输出；
4. 为 Unknown sibling 和 Temporal Opportunity 指定正式 owner 或保留明确的 Working seam；
5. 再决定哪些数值值得标定，哪些设计应删除。
