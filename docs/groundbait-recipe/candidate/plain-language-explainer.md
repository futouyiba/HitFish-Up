# 台钓窝料 / 混饵机制：深入浅出说明

> 状态：Candidate Explainer  
> 日期：2026-10-28  
> 用途：帮助设计者、程序和后续 Agent 快速理解当前提案。机制细节以 `proposal.md` 和子模块文档为准。

## 一句话

这套设计不是“把几个饵料加分项相加”。

更接近：

> 玩家调出一团饵。饵在水里释放食物、化学线索和颗粒；不同鱼根据自己的食性、体型、摄食结构和当前状态，对这些东西产生不同反应。

## 1. 一份配方同时包含四类事实

假设玩家调：

```text
60% 谷物基础饵
25% 虾粉
10% 红虫粉
5% 状态粉
+ 少量草莓小药
```

系统不直接算：

```text
谷物 +0.3
虾粉 +0.4
红虫 +0.2
小药 +0.1
= 总分 1.0
```

而是先拆成四个问题：

```text
这团饵里有什么可吃的东西？
→ Food

释放什么化学线索？
→ Flavor / Chemical Cue

实体颗粒有多大？
→ Particle Size

这些东西如何在水里解体、扩散、沉降和持续？
→ Physical Release
```

四者职责不同。

## 2. Food：鱼到底想吃什么

例如：

```text
谷物
虫
甲壳类
植物
藻类
```

鲤鱼可能同时喜欢谷物和甲壳类。

当前算法候选是：同一种 Food Target 的有效 Exposure 先合并，再做边际递减。

因此，如果甲壳类信号已经很强，继续堆虾粉的边际收益可能变小；如果目标鱼同时也喜欢虫类，转一部分预算给红虫粉可能更值。

但这不是“混得越多越强”。如果目标鱼根本不喜欢虫，混红虫没有理由自动变好。

## 3. Flavor：不是原料质量百分比，而是最终 Cue Exposure

Flavor 不能做成：

```text
腥 Bonus
+ 奶 Bonus
+ 果香 Bonus
+ 蒜香 Bonus
```

否则玩家最优策略很容易变成“每种都来一点”。

当前候选先计算：

```text
Ingredient amount / dose
× 这个 Ingredient 对某味型的 Cue Potency
→ 该味型的 Cue Exposure
```

再得到：

```text
Flavor Composition
→ 各味型在总 Cue Exposure 里的相对组成

Flavor Intensity
→ 总体化学线索有多强
```

例如最后可能得到：

```text
腥    40%
谷香  30%
果香  20%
奶香  10%
```

这里的 40% 不是说“配方质量里 40% 是腥味原料”，而是说腥味占当前 Chemical Cue Exposure 的约 40%。

所以少量高 Potency 小药完全可能显著改变味型画像。

## 4. 小药：不是 Buff 药水

当前更合适的理解是：

> 小药是低剂量、高 Potency 的 Chemical Cue Modifier。

它主要改变：

```text
Cue Exposure
Flavor Composition
Flavor Intensity
```

而不是：

```text
基础配方效果 + 小药固定加成
```

如果目标鱼喜欢被推过去的新味型，可能变好；如果不喜欢，新味型也会稀释原有组成，结果可能变差。

## 5. Particle Size：筛选谁能有效利用实体食物

颗粒大小和拟饵大小筛选很像，但不是简单比较“颗粒 < 鱼嘴”。

鱼侧先看：

```text
鱼当前的线性体尺，例如体长
+ 口部 / 过滤结构
+ 它用什么方式吃东西
```

这里要特别区分：

- 体长等线性尺度可以和口部比例一起生成一个长度 Reference。
- 鱼重不能直接乘一个 Mouth Ratio 得到颗粒毫米数，量纲不成立。
- FILTER 也不强迫走“体长 × 嘴比例”，它可能主要由鳃耙 / 过滤结构决定有效截留粒径。

所以鱼侧不直接配置“最佳 5 mm”，而是生成 Size Response。

### Groundbait

窝料输入是一组粒径分布：

```text
Fine    20%
Small   40%
Medium  30%
Coarse  10%
```

小鱼对大颗粒的可利用性可能快速下降；大鱼通常可以利用更宽范围。配方变粗以后，小鱼可利用份额下降，就能自然形成体型筛选。

不需要额外写：

```text
大颗粒 → 大鱼概率 +30%
```

同时，当前模型不默认“大鱼因为嘴大，所以强烈讨厌小颗粒”。左侧细颗粒效率应该由摄食方式决定，而不是统一降到 0。

### Hookbait

以后钩上饵球可以复用“尺寸是否适合摄食”这一层：

```text
饵球大小 × Fish Size Response → Size Fit
```

但 Hookbait 还有形状、硬度、钩体阻碍、持钩、姿态等额外问题。复用的是尺寸语言，不是把 Groundbait 整套响应直接搬过去。

## 6. 多种摄食方式不是多份 Bonus

一条鱼可能既会底吸，也会啄食。

当前首轮候选不是把两个 Fit 相加，而是：

> 面对同一个食物对象，比较几种可用摄食方式，先测试“采用当前最有效路径”的 best-path 方案。

这样不会出现“会的摄食方式越多，Size Fit 就越高”的套利。

但具体用 `max` 还是平滑 best-path 仍要由 Gold Fixture 决定，不能把 `max` 当成已经确认的正式公式。

## 7. 雾化、黏度：决定信号怎么传播，不直接加中鱼

高雾化不等于“更强”。它可能意味着：

```text
解体更快
→ 细颗粒和 Chemical Cue 更快释放
→ 更快形成明显信号
→ 可能更容易快速开窝
```

同时也可能带来：

```text
释放快
→ 消耗快
→ 更需要补窝

扩散广
→ 可能更容易招到非目标鱼
```

黏度、比重等也应先进入解体、沉降、扩散和持续过程。

这里还没有确认“高黏度必然更集中、更持久”这样的硬公式。我们要验证的是能否稳定形成：

```text
快速开窝
vs
长期守窝
```

以及其它有明确代价的打法，而不是追求“雾化值越高越好”。

## 8. Food 和 Flavor 的关系

Food 和 Flavor 相关，但不是一回事。

例如虾粉同时可能带来：

```text
甲壳类实体食物
+ 腥 / 海产类 Chemical Cue Potential
+ 自己的颗粒和物理性质
```

草莓小药可能几乎不贡献实体食物，但提供很强的果香 Chemical Cue。

因此：

```text
Food
→ 有什么可以吃

Flavor / Chemical Cue
→ 水里释放了什么可被鱼感知的化学线索
```

它们可能在后续分别影响发现、趋近、摄食、留鱼等不同过程，但这些中间语义还没闭合，不提前锁死成一条总公式。

## 9. “不喜欢”和“排斥”不同

如果一条鱼对蒜味只是没有兴趣：

```text
蒜味没有正向帮助
```

如果它对强蒜味存在 Avoidance：

```text
蒜味出现反而降低响应
```

当前只计划稀疏配置少数这种关系，不给所有 Fish × Flavor 填满正负矩阵。

## 10. 天气暂时不直接决定“今天喜欢什么味”

当前较稳的边界是：

```text
天气 / 时段等环境输入
→ 现有 Fish Condition / Feeding Readiness / Activity
→ 当前响应积极程度变化
```

而不是：

```text
下雨 → 一定喜欢腥
晴天 → 一定喜欢果香
```

Diet Shift 是否需要、由什么驱动仍是 Open。较慢生态 Context 或有界随机漂移都只能作为后续候选，不能提前写成既定机制；唯一已经排除的是“每杆随机改食性”。

## 11. 玩家最终应该在想什么

后台机制可以复杂，但玩家心智最好仍然简单：

```text
目标鱼吃什么？
今天鱼口怎么样？
我现在想筛小鱼还是筛大鱼？
我要快开窝还是长时间守？
现在的味型需要往哪个方向调？
```

好的配方不应该是“把所有好东西全塞进去”，而应该有明确目的和代价。

## 12. 当前最重要的下一步

不是继续发明更多参数。

先用 `Edible Size Response` 做一个小型 Gold Fixture，验证：

- 同物种线性体尺变化后，尺寸响应是否合理移动；
- 不同口部形态是否产生可解释差异；
- 啄食、吸食、吞食、滤食是否真的需要不同曲线；
- FILTER 是否可以脱离 Mouth Reference 工作；
- 粗颗粒能否筛小鱼；
- 细颗粒是否不会无依据地强烈排斥大鱼；
- 多摄食方式不会叠加套利；
- best-path 的 `max` 是否会产生不合理的尖锐切换。

这条链跑通以后，再接 Groundbait Particle Distribution 和 Physical Release。
