# 打窝的时间模型：先看水里还剩什么

> Candidate / Working Experiment，2026-11-04。承接用户指定的持久响应方向，不是生产持久化 Contract。

## 1. 发窝不等于生成鱼

刚投入的窝料未必立刻成为当前水层可接触的食物。候选用“尚未释放”和“当前可用”两份库存，解释延迟。背景作用随可用对象增加而出现；库存流失后衰退。这里的发窝是 Response 变化，不是鱼数增加、迁移或新增 Opportunity。

同一批物料快释放和慢释放会有不同早晚排序。玩家投量与补窝时点有意义，不需要另加一个随时间自动增长的发窝奖励。

## 2. 最小精确转移

每批可食对象保存未释放量 D、当前可用量 A。释放率 r、离开/不可处理合并率 l 均非负，当前实验只取常数：

```text
dD/dt = -rD
dA/dt = rD-lA
```

时间差 Δ：

```text
D' = D exp(-rΔ)
A' = A exp(-lΔ) + rD [exp(-rΔ)-exp(-lΔ)]/(l-r), r≠l
A' = A exp(-lΔ) + rD Δ exp(-lΔ), r=l
流失增量 = D+A-D'-A'
```

这给出精确的恒率解。实现用 `expm1` 计算近等速率的指数差商，避免大数相减丢失释放量；测试覆盖 r 与 l 仅相差一个浮点步长。在线小步和离线大步在浮点误差内相等。r=0 时不释放，r=l 分支避免除零。若环境、释放率发生变化，要在变化时点分段，不能沿用整个离线时段恒率假设。

与 [physical-release.md](physical-release.md) 的账本关系：D 是显式化的未释放库；该页当前可用 A 不能再包含相同 D。实验把“离开”与“不可处理”合并为 lost，故只验证 `D+A+lost+consumed=deposited`，不冒称已实现细粒度 L/U 或载体账本。每批保留自身释放率，不能先把快慢批次平均后推演。

## 3. 过剩与饱食分开

物料过剩用 [钩饵组合式](hookbait-groundbait-combination.md) 的竞争分母表达，不推断发生摄食。

只有确认的摄食事件才可产生压力：

```text
eaten = min(confirmed_event_mass, current_available)
A_lot' = A_lot × (1-eaten/Σ A)
P' = P + κ eaten
无摄食期间：P(t+Δ) = P(t) exp(-ρΔ)
```

事件后的质量从可用库扣除，不能重复吃同一物料。P 只是地点响应记忆，不叫“鱼真的饱了”；目前未按鱼种区分，不能让它成为生产全鱼种饱食。若需要鱼种/模式专属压力，必须有摄食归属和该压力购买的独立策略，不能把一个总压力广播给所有物种。

Probe 不自己生成摄食事件。离线期间默认只做物理与既有压力衰减，无摄食输入；这明确意味着离线不会凭空继续积累饱食。若游戏要求无人在线时仍有摄食，必须增加服务器摄食生产者并验证事件来源，不用固定扣量伪装成鱼在吃。

## 4. 时间样本

所有时间、质量与参数都是 Working Fixture。输入和完整输出见 [JSON](../fixtures/float-strategy-v1-results.json)。H固定0.4，β=6，γ=0.5，r=0.2，l=0.03。表格数字从运行输出摘取，细值以JSON为准。

| 方案 | 投放计划 | 玩家取舍 |
|---|---|---|
| 不打窝 | 无 | 保持钩饵自身价值，不产生物料成本 |
| 适量 | t=0投2单位 | 等待释放，再随库存流失衰退 |
| 连续补 | t=0至30，每5单位时间投2单位 | 后期库存叠加，可能增加竞争，不能每次重置发窝计时 |
| 过量 | t=0投30单位 | 高可用量可能低于适量方案；P仍为0 |
| 快/慢 | 同为2单位，r=0.6/0.04 | 早晚窗口互换，不是一个永远胜出 |
| 确认摄食 | 投2单位，t=10确认摄食0.5 | 库存扣减且P增加，之后恢复 |
| 第二玩家 | A在0投2，B在10投2 | 同一共享作用域增量，不给每人复制一窝 |

固定时点的实际运行结果如下，数值为 `C_trial`，不是概率：

| 时点 | 不打窝 | 适量 | 连续补 | 过量 | 快释放 | 慢释放 |

| 5 | 0.4000 | 1.0689 | 1.0689 | 0.2753 | 1.0323 | 0.8591 |
| 10 | 0.4000 | 1.0571 | 0.9294 | 0.2304 | 1.0468 | 0.9871 |
| 30 | 0.4000 | 1.0639 | 0.5419 | 0.3250 | 1.0552 | 1.0537 |
| 60 | 0.4000 | 0.8975 | 0.7312 | 0.6252 | 0.8685 | 0.9989 |
| 120 | 0.4000 | 0.5280 | 1.0366 | 1.0648 | 0.5157 | 0.6671 |

过量方案在后期可恢复到较高值，这使“马上补窝”与“等库存下降”形成取舍。它也暴露限制：若未来收益只看无限长时间积分且完全不计成本，过量初投可能变成提前购买未来窗口。生产评估必须固定作钓时长、材料成本和目标鱼构成，不能只选最好看的一个时点。

脚本对24小时或真实分钟不作解释。过量降低响应并非参数无关结论；γ=0时本实验不会出现物料竞争，必须作为负对照保留。

## 5. 保存、重登与多人语义

最小实验保存：作用域、求值时点、每批库存/率/来源、已处理事件ID、摄食累计与压力。重登先按时间推演，再读取派生响应。不能保存一个“窝强度”后又把原始事件重新全加一遍。

实验采用 `room:cell:layer` 共享作用域，actor只记来源，不复制物理库。这个选择只供测试，不裁定正式公共/私有语义：

- 若产品选玩家私有，把player纳入作用域；别让同一共享库存再被每人扣一次。
- 若选公共水域，必须确定跨实例的水体身份、并发提交与占用规则。
- 同时点事件由服务器排序；重复ID无操作。过晚事件拒绝并要求从检查点重放，不把时间倒退或硬夹到现在。
- 在线和重登使用同一恒率求值；Snapshot带机制版本。版本迁移失败不能拿新率解旧状态。
- 时间基准（现实/游戏）、最大离线时长、过期阈值和清理窗口仍须Owner决定。

探针按每批对象O(N)计算，事件去重集合与批次均无限增长，所以不是生产可扩展后端。候选压缩只合并相同作用域、机制版本、Food/对象状态和释放率的批次，并保留来源审计摘要。仅剩同率线性库存时可以合并；有摄食归属差异则不能随意合并。去重必须覆盖仍可能重试的事件期限，不能清集合后接收旧事件再加料。

## 6. 已运行的边界

- 恒率在线60小步与离线1大步，包括r=l分支一致。
- JSON保存/加载后，同一摄食事件重发无效；继续求值与原状态一致。
- 两玩家同一时间的投放顺序不改聚合物理结果；跨房间事件拒绝。
- 没有摄食输入时，再大量投放也不会增加P。
- 当前实验没有修改DEF、Fish Condition、L的写入口。隔离测试仅证明此脚本的结构，不是现有生产系统的集成测试。

这些结果只验证最小模型可算。真实发窝、适量、过量与恢复的时间尺度没有生产标定；状态饵到释放率的映射也未闭合。
